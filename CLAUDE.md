# SpecMate — repository conventions

## The web app is drawn from one kit

Three layers, and a change belongs to exactly one of them:

- `apps/web/src/theme/theme.css` — every colour and typeface, one block per theme. A component
  names a role (`primary`, `warning`, `destructive`, `info`, `success`, the four greys, mono,
  sans); the theme decides what it looks like. The names are shadcn's; the roles shadcn has no
  word for are declared beside them, and the ones that are a wash of the page (`secondary`,
  `muted`, `accent`) are computed once in `index.css` rather than nine times here.
- `apps/web/src/index.css` — the palette, the four motions, and what is left that a utility cannot
  say: the diff's rows, the syntax hues, the markdown face, the scrollbar. Everything else that
  used to live here is a variant table now.
- `apps/web/src/ui` — the React kit: a name and a typed set of choices per part, written as `cva`
  tables over shadcn's components. **Nothing outside `src/ui` assembles a part.** `Button`, not a
  hand-written row of utilities; `Select`, not `@radix-ui/react-select`.

The parts are adapted from shadcn rather than generated by its CLI. The CLI writes `@/`-aliased
imports into `components/ui`, and this repo has neither — imports are relative and carry their
extension. Take the component's source, keep its structure, and fit it to the kit: one exported
name, `cn(…, className)` last, and the choices as `cva` variants.

Two libraries stay behind the kit, for the same reason and enforced the same way. `ui/icon.tsx` is
the only file that names `lucide-react`; marks are addressed by what they mean here (`check`,
`unfold`, `pull-request`) at one size scale and one stroke weight. And only `src/ui` imports
`@radix-ui/*` — a `Select` opened straight from Radix at a call site is a control the theme
switcher never sees and the workbench never renders. Nothing is drawn by hand and nothing is typed
as a glyph: a `⌄` or a `✓` in JSX takes the metrics of whatever face it lands in and goes into the
element's accessible name.

A call site owns its layout — every primitive takes a `className` and appends it last through `cn`,
which is `clsx` plus `tailwind-merge`. The merge is what makes that true: a variant table writes
utilities too, so `px-4` from the part and `px-8` from the caller are two rules of equal weight, and
without merging the winner would be Tailwind's emission order rather than the attribute's.

`ui/kit-discipline.test.ts` enforces all of it: no kit class outside the kit, every colour utility
naming a role the theme actually defines, only `tone.ts` lighting a signal role, one importer of the
icon library, no importer of a primitive outside `src/ui`, and no mark typed as a glyph.

`/kit` renders every part in every variant and state under the theme switcher. Look at it after
changing anything in `src/ui`, and add the new part to it.

## Tests are written on vitest

New tests are written on **vitest**, and use what it actually gives you rather than hand-rolled
scaffolding: `vi.fn` / `vi.spyOn` for doubles, `vi.mock` for module boundaries,
`vi.useFakeTimers` for clocks, `test.each` for tables, `expect.soft` when several assertions on
one subject should all report, `expect.poll` / `vi.waitFor` for eventually-true conditions,
`toMatchObject` and the asymmetric matchers instead of assembling comparisons by hand. Nothing is
global — `globals: false` everywhere, so every import is explicit.

Do not write new `bun:test` files, and do not reach for bun's built-in `expect`.

Where each suite runs today:

- `apps/web` — vitest + jsdom + testing-library (`bun run --cwd apps/web test`).
- `packages/core` — vitest under the root `vitest.config.ts` (`bun run vitest run`).
- everything else — still `bun test` (`bun run test:bun`), because those suites import the Bun
  runtime itself: `packages/db` imports `SQL` from `bun`, and the workspace and runner packages
  call `Bun.spawn`, `Bun.$`, `Bun.file` and `Bun.write`. Vitest's workers are Node, so those
  files cannot move until the code under them stops binding to Bun. A wholesale migration is not
  planned; move a suite when the code it covers stops needing Bun.

`bun run test` runs all three.
