Design

The task view reads five sources on every render: the task detail, the event window, the conversation's messages and actions, the decision rows, and the artifact index. Before this change all five were rendered as sibling panels down one column, each with its own border, uppercase label, and heading — which is why nothing on the screen looked more important than anything else.

Decisions

Chapters are derived from stageId plus the state timeline, not from a new field. buildThread walks entries in ledger order, carrying the task's state as it goes.

  • An entry belongs to a stage when it names one.
  • Failing that, when it falls inside a stage's [startedAt, finishedAt] window.
  • Everything else falls to the state the task was in.

One caveat the console must not lie about. A stage assembles its prompt once, at dispatch — executor.ts loads the ledger a single time per run — so text typed while Implement is running reaches Implement on its next run, not mid-flight. That is what the wording here says. Reaching a live agent needs a channel that does not exist yet, and is its own change. Worse, an intervention claimed by a run that then fails is not re-claimed by the retry and stops being rendered at all — so the writer this design needs comes with a one-line fix to the claim, not without it.

Open questions worth a yes/no: does Files drop the pipeline rail (it does here — the diff needs the width), does the per-file 💬 comment post into the thread anchored to that path, and which fix for the lost-on-retry intervention — never stamp until a run is accepted, or clear the stamp whenever a stage ends unaccepted?
